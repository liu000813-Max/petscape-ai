# ADR-0003：PostgreSQL 任务表与 SKIP LOCKED Worker

- 状态：Accepted（2026-07-17 终审通过）
- 决定日期：2026-07-17
- 适用阶段：Phase B 起

## 背景

PetScape 的图片生成、3D 生成、模型解析、几何处理和切片属于分钟至小时级任务。任务量预计为每天几十至几百个，吞吐和毫秒级投递延迟不是主要矛盾；幂等、恢复、供应商状态追踪、防止旧结果覆盖和可解释错误才是核心要求。

系统已经需要一份拥有所有者、输入、进度、错误和结果引用的持久任务记录。团队不希望为了低吞吐任务额外运维 Redis 或云消息产品。

## 决定

在业务 RDS PostgreSQL 中建立受“生成任务”模块拥有的任务表，由独立 Worker 使用事务和 `SELECT … FOR UPDATE SKIP LOCKED` 轮询认领。

第一阶段不引入 pg-boss、graphile-worker、BullMQ、Redis、MNS、RocketMQ 或 SchedulerX。任务表是本地任务状态真相源；外部供应商任务 ID 是可追踪引用，不取代本地状态。

任务实现必须同时具备以下机制：

1. **租约与心跳**：认领时写入 Worker、`lease_expires_at` 和 attempt；执行期间周期续租。分钟级与小时级任务使用按类型配置的租约和心跳参数，不共享一个固定超时；
2. **孤儿任务恢复**：租约过期只允许进入恢复判断。存在供应商任务 ID 时，重新提交或重新执行前必须先查询供应商侧状态；
3. **防迟到覆盖**：任务携带目标对象版本、generation 或等价并发令牌；完成写入时执行条件更新，旧任务不能覆盖更新版本；
4. **业务幂等**：副作用入口生成业务幂等键，并以数据库唯一索引保证同一用户、同一输入和同一操作不会重复创建付费副作用；
5. **错误分类**：将错误规范化为可重试、永久失败、取消和需要人工处理等类别；重试策略按任务类型配置并记录每次 attempt；
6. **归档策略**：任务、attempt 和详细日志有明确在线保留与归档规则，避免活跃索引无限增长；订单证据引用不得随普通任务清理；
7. **原子状态变化**：任务创建可与业务状态在同一事务提交；认领、续租、完成、失败和取消使用带前置状态/版本条件的更新；
8. **竞态测试**：至少覆盖杀死 Worker、并发认领、租约过期恢复、供应商已完成但本地未落库、旧任务迟到完成和重复幂等请求。

初始轮询允许秒级延迟。`LISTEN/NOTIFY`、多张调度表、分区表和独立消息系统都不是 Phase B 基座前置。

## 关键理由

- RDS 已经是必需基础设施，任务表不增加新的运行组件；
- 日几十至几百任务远低于 PostgreSQL 队列表的常见争用区间，几秒轮询延迟对长任务可忽略；
- 业务幂等、供应商恢复和版本防覆盖无法由通用队列库自动理解，仍需在业务层设计；
- 任务创建与业务记录可在同一事务完成，避免数据库与 Redis/MQ 双写不一致；
- 自有表结构可以直接表达 ARCHITECTURE.md 已确认的所有者、输入、租约、进度、供应商引用和结果引用；
- 保留 PostgreSQL 原语和清晰 Port，未来吞吐或团队规模变化时仍可替换认领实现。

## 放弃的备选

### pg-boss

它复用 PostgreSQL 并提供成熟调度、重试和维护能力，是首要后备方案。但业务幂等、供应商孤儿恢复、长任务细粒度续租和版本防覆盖仍需自建；当前收益不足以抵消额外抽象和库维护依赖。

### graphile-worker

具备 PostgreSQL 与 heartbeat 能力，但引入另一套任务抽象和运维知识。当前低吞吐场景不需要其更多调度能力。

### BullMQ 与 Redis

会让任务业务状态位于 PostgreSQL、投递状态位于 Redis，形成双写和恢复一致性问题，并增加 Redis 持久化、内存策略与监控责任。

### 阿里云 MNS、RocketMQ 或 SchedulerX

这些产品解决消息投递或调度，不能替代拥有幂等键、进度、租约和结果引用的业务任务记录；当前只增加云产品依赖和 SDK 学习面。

### Web 进程内后台 Promise

无法跨重启恢复，也不能稳定支持租约、并发认领和独立扩缩，明确退出正式路径。

## 已知代价与风险

- 自研代码量不大，但租约、恢复和竞态正确性要求高，测试不足会把“简单”变成“简陋”；
- 纯轮询会产生固定查询开销和数秒认领延迟；
- 任务表与索引长期增长会影响认领性能，需要归档和清理；
- 高并发下 `SKIP LOCKED` 仍可能产生锁与扫描争用；当前量级接受，增长后重评；
- 供应商 API 无法查询状态或返回不一致时，孤儿恢复可能需要人工介入；
- Worker 进程被暂停但未退出时，租约参数不合理可能产生重复执行；
- 数据库故障会同时暂停业务事务和任务领取，这是选择单一协调系统的代价。

## 验证条件

Phase B 的持久任务链只有在以下真实 PostgreSQL 证据通过后才成立：

1. 用所选 RDS PostgreSQL 版本验证 `SKIP LOCKED` 认领 SQL、事务隔离级别和 Prisma raw SQL 接驳方式；
2. 两个以上 Worker 并发认领同一批任务，证明每个 attempt 只有一个租约持有者；
3. 分别对分钟级和小时级模拟任务验证心跳续租、失联和租约过期；
4. 强制杀死 Worker，证明新 Worker 能认领孤儿任务，并在存在供应商任务 ID 时先查状态而不是重复提交；
5. 制造旧任务迟到完成，证明条件更新无法覆盖更新版本；
6. 并发发送相同幂等请求，证明唯一索引只允许一个付费任务成立；
7. 覆盖可重试、永久失败、取消和人工处理分类，并验证重试上限；
8. 明确任务与 attempt 的在线保留期、归档执行方式、查询索引和清理失败告警；
9. 以预期峰值的显著倍数做小型争用测试，记录重新评估 pg-boss、分区或独立消息系统的触发指标。

pg-boss 是否具有专门业务幂等 API、MySQL `SKIP LOCKED` 生态成熟度、Redis 实时价格以及阿里云 MQ SDK 质量都不阻塞本决策；仅在重新打开相应备选时重新核实。
