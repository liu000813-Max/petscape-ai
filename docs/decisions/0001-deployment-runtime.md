# ADR-0001：单台 ECS 与 Docker Compose 部署形态

- 状态：Accepted（2026-07-17 终审通过）
- 决定日期：2026-07-17
- 适用阶段：Phase B 起

## 背景

PetScape 第一阶段需要同时运行 Next.js Web/API 与独立 Worker。Worker 会执行分钟至小时级任务，并需要能够承载 Python 环境、本地几何处理库和切片二进制；团队规模为 1–2 人，不应为尚未出现的流量提前承担 Kubernetes 或多节点调度复杂度。

目标市场为中国大陆，运行边界限定在阿里云生态。关系型数据库与对象存储使用云托管服务，不随应用容器自建。

## 决定

第一阶段采用一台阿里云 ECS，通过 Docker Compose 运行两个应用进程：

- `web`：Next.js standalone 容器，承载 Web、Route Handler 与共同 HTTP API；
- `worker`：独立重镜像，承载任务入口以及当前迁移链需要的 Python、trimesh、PrusaSlicer 等本地运行依赖。

Web 与 Worker：

- 同仓库、同主机部署；
- 共享应用层、领域模块、Prisma Client 与数据契约；
- 分别构建镜像、设置资源限制、健康检查和重启策略；
- 通过 RDS PostgreSQL 中的持久任务交接工作；
- 共同访问托管 RDS 与私有 OSS，不在 Compose 中运行 PostgreSQL、Redis 或对象存储。

CI/CD 采用：

1. GitHub Actions 构建 Web 与 Worker 镜像；
2. 使用不可变 tag 推送到阿里云容器镜像服务 ACR；
3. 通过 SSH 让 ECS 拉取指定 tag 并执行 Docker Compose 更新；
4. 回滚时恢复上一组已验证镜像 tag，再次执行 Compose 更新。

国内节点在备案完成前不作为公开 HTTP(S) 入口。备案期间只允许本地、内网或另行批准的测试环境承担验证。

单台 ECS 是已接受的第一阶段单点。通过 ECS 快照、版本化 Compose 配置、不可变镜像 tag 和可演练的重建步骤降低恢复时间，但不声称具备自动故障转移。

本 ADR 只确定部署承载形态。Worker 镜像需要容纳当前重工具链，不等于长期确认 trimesh 与 PrusaSlicer；模型处理与切片技术仍由单独 ADR 决定，替换工具不应改变 Web/Worker 双进程边界。

## 关键理由

- ECS 没有函数执行时长和未解压镜像大小的 Serverless 舒适区限制，适合大镜像与小时级任务；
- Docker Compose 足以表达当前两个进程及其健康检查，不需要预付 Kubernetes 运维成本；
- Web 与 Worker 分镜像可避免把本地二进制塞入轻量 Web 镜像，也允许分别重启和设定资源上限；
- RDS、OSS 保持托管，避免把数据库备份、高可用和对象耐久性责任转回单机；
- GitHub Actions、ACR、SSH 和不可变 tag 构成简单、可复现且可回滚的发布链；
- 容器化保留未来把 Web 迁往 SAE、把 Worker 迁往多机调度平台的可能，但当前不提前实施。

## 放弃的备选

### SAE 承载全部服务

SAE 更适合常驻 Web 和微服务。Worker 的大镜像、长任务与本地二进制会增加适配和排障不确定性；当前没有足够收益抵消平台约束。

### 函数计算 FC

即使执行时长可能覆盖部分小时级任务，镜像大小、长时间计费、进程模型和本地工具链仍与当前 Worker 不匹配。它不作为第一阶段生产承载。

### ACK/ACS 或多台 ECS

能够提供更强调度和容错，但当前流量、团队规模和运维能力不足以证明其复杂度。出现多机并发、容量隔离或明确可用性目标后再评估。

### 在 Compose 中自建数据库、Redis 或对象存储

会把数据耐久性、备份、恢复和单机故障风险全部压回 ECS。本项目已选择托管 RDS、OSS，并选择不依赖 Redis 的持久任务方案。

## 已知代价与风险

- ECS 故障会同时中断 Web 与 Worker，没有自动故障转移；
- Worker CPU、内存或磁盘耗尽可能影响同机 Web，必须设置容器资源限制并监控宿主机；
- Worker 重镜像会增加构建、推送、拉取和回滚时间；
- SSH 发布需要安全管理 GitHub Actions、ACR 与 ECS 凭证；
- Docker Compose 更新可能产生短暂服务中断，第一阶段接受，支付和订单上线前需重新评估；
- 快照只能降低重建成本，不能替代配置可重现、数据库恢复演练和应用级回滚；
- 备案进度是国内公开上线的外部前置条件。

## 验证条件

Phase B 实施前或实施中必须用可执行证据关闭以下条件：

1. 构建 Web standalone 镜像，验证 `public/`、`.next/static`、Sharp、流式响应和启动环境校验在目标 Linux 架构下正常；
2. 构建 Worker 镜像并记录实际压缩/解压体积、构建时间、拉取时间、磁盘余量以及 trimesh/PrusaSlicer 的目标架构可执行性；
3. 在 ACR 控制台复核所选版本的容量、镜像大小、保留策略、并发拉取限制、价格与 SLA；调研未核实的企业版价格和个人版配额不得写成已确认事实；
4. 完成一次 GitHub Actions → ACR → ECS 的部署演练，以及一次恢复上一不可变 tag 的回滚演练；
5. 验证 Web 与 Worker 的健康检查、资源限制、日志轮转和宿主机磁盘告警；
6. 通过阿里云当前规则或工单复核备案期间域名/IP 的实际访问限制，不依赖历史社区口径安排上线；
7. 完成 ECS 快照恢复或新机重建演练，并记录可接受的恢复时间；支付和订单上线前补齐第 10 节要求的正式回滚与恢复能力。

SAE Job 最大时长、FC 24 小时上限等未核实数字不是本决策的实施前置；只有重新打开 Serverless 备选时才需重新核实。
