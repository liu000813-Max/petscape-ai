# ADR-0004：Better Auth、PNVS 与多端凭证模型

- 状态：Accepted（2026-07-17 终审通过）
- 决定日期：2026-07-17
- 适用阶段：Phase B 起

## 背景

PetScape 首发面向中国大陆，并需要从第一天保留 Web、未来 App 与微信小程序共享同一用户身份的能力。当前可用资质支持阿里云号码认证服务 PNVS 的短信验证码，但微信网站登录、小程序电商类目和支付仍受执照与平台审核约束。

手机号、微信和未来登录方式不能成为业务对象主键；用户换绑手机号或增加客户端时，项目、资产和订单归属必须保持稳定。

## 决定

采用 Better Auth 作为身份与会话框架，启用官方 `phone-number` 插件，并通过其 `sendOTP` 适配器调用阿里云 PNVS 发送短信验证码。

第一阶段的职责划分为：

- Better Auth 负责验证码生成、保存、过期、尝试次数、防暴力验证、验证结果和 Session；
- PNVS 只作为短信发送通道，不成为本地用户、验证码或 Session 的真相源；
- PNVS SDK 和供应商错误映射封装在身份基础设施适配器中；
- Next.js Route Handler 只建立身份上下文并调用身份应用用例；
- 业务模块只引用稳定 `User.id`，不依赖 Better Auth 表、手机号或微信标识。

身份数据从第一天使用“用户 + 多凭证”模型：

- `User` 保存稳定内部身份与账号状态；
- 独立 credentials/account 记录保存手机号、邮箱、微信等登录凭证并归属同一 User；
- 手机号是可验证、可换绑的 credential，不是 User 主键；
- 微信 `unionid` 与 `openid` 保持不同语义和存储位置，`openid` 还必须区分网站、小程序、App 等客户端；
- 数据模型预留微信凭证扩展能力，但微信登录和小程序接入只在执照、开放平台绑定与对应审核条件满足后实施；
- 凭证绑定、解绑、冲突合并和恢复必须留下审计记录，高风险操作需要重新验证。

Phase B 正式落地前先做 tracer：

1. 验证选定 Better Auth 版本与 Next.js 16、项目 Node.js 版本和 production build 兼容；
2. 验证 Better Auth Prisma adapter 与既定 Prisma migration 流程共存；
3. 使用真实 PNVS 测试账号打通验证码发送、验证、限流、Session 和失败映射；
4. tracer 通过后才进入正式身份模块实现。

## 关键理由

- Better Auth `phone-number` 插件已经覆盖 OTP 生命周期、尝试限制与 Session，项目只需适配短信发送通道；
- PNVS 允许当前个人资质用于登录验证码，不必等待传统 SMS 品牌签名或企业资质；
- Better Auth 相比 Auth.js Credentials 路径减少验证码存储、校验、限流和会话自研面；
- 独立凭证模型支持手机号换绑，以及未来 Web、微信小程序和 App 绑定到同一 User；
- `unionid` 与分端 `openid` 明确分离，避免把不同微信应用中的同一用户永久拆成多个业务身份；
- 身份框架被限制在适配器和入口层，不让供应商或框架数据模型扩散到业务模块。

## 放弃的备选

### Auth.js v5 与 Credentials Provider

生态成熟，但手机号验证码需要自行实现生成、存储、过期、尝试限制、防重放和 Session 衔接。Better Auth 已提供更小的自研面。

### Lucia

已经停止维护，不进入正式工程基座。

### 完全自研 Session 与短信认证

能够控制全部细节，但会重复实现安全敏感的验证码与会话基础能力，不适合当前团队规模。

### 阿里云 IDaaS

定位和成本面向企业级统一身份治理，对单一 C 端产品过重，也不会消除微信多端凭证建模问题。

### 立即接入微信登录或把微信标识作为 User 主键

当前资质与电商类目不满足上线条件；`openid` 还是单应用标识，直接作为主键会破坏多端账号统一。

## 已知代价与风险

- Better Auth 仍在活跃演进，Next.js 16 peer dependency、缓存和构建兼容性必须以 tracer 为准；
- 未找到 Better Auth + PNVS 的成熟中文实战，供应商适配和异常处理需要自行验证；
- PNVS 预置短信签名可能不展示 PetScape 品牌，影响用户信任和体验；
- Better Auth 插件对“已有账号绑定手机号”、凭证冲突、账号合并和恢复的边缘行为尚未全部核实；
- 短信登录会带来发送成本、滥用、撞库、SIM 换卡和号码回收风险；
- 未来微信多端只有在相关应用绑定同一微信开放平台账号并取得一致 `unionid` 时才能可靠自动关联；
- credentials 表预留扩展位不等于提前实现微信业务逻辑，过度预建字段仍可能随官方协议变化。

## 验证条件

身份基座必须关闭以下条件：

1. 锁定 Better Auth 版本，并用当前 Next.js 16 生产构建、Route Handler、Cookie/Session 和 Web/Worker 共享身份查询跑 tracer；确认历史 peer dependency issue 在所选版本中不再复现；
2. 验证 Prisma adapter 生成表、migration、索引和既有 `User`/credential 边界，避免 Better Auth schema 成为业务模块的公共模型；
3. 用个人实名认证账号验证 PNVS `SendSmsVerifyCode` 的实际开通、配额、限流、错误码、送达率和费用；
4. 实测 PNVS 预置签名的用户可见内容，确认是否可接受；若影响明显，在登录模块实现前提交用户体验确认；
5. 验证插件验证码有效期、允许尝试次数、重复发送、并发验证、手机号规范化、Session 撤销和审计记录；
6. 验证“已有用户绑定手机号、手机号已属于另一用户、换绑和账号恢复”行为；报告未核实的插件边缘能力不能靠假设进入生产；
7. 在微信接入前，用微信官方当前文档与真实开放平台配置复核网站应用资质、个体工商户电商类目、`unionid` 获取条件及三端 `openid` 归属；
8. 微信登录上线前专项验证同一用户在 Web、小程序和 App 中的 unionid 一致性；无法取得时必须走明确绑定流程，不自动猜测合并。

传统阿里云 SMS、自定义品牌签名迁移路径和 Auth.js v5 的 Next.js 16 兼容性不是当前实施阻塞；只有切换通道或框架时再重新核实。
