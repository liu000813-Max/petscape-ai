## 本文件的准入与分层规则

约束的落点按上下文税从低到高分四层，**能落在上层的绝不落下层**：

1. **lint / CI 强制**——机器判定，零上下文税（现有：ESLint 边界规则、`lint:baseline`、CI 集成测试门禁）；
2. **目录级 CLAUDE.md**——只有动到该目录才注入（现有：`packages/server/CLAUDE.md`）；
3. **本文件**——已拍板、机器管不住、散落即失传的约束正本（含理由与演化记录）；
4. **根 CLAUDE.md**——只留全局硬约束和指向本文件的一行指针。

收录门槛：每条必须写清「不遵守会发生什么事故」，答不出具体事故场景就不收录；清单宁缺勿滥。某条约束一旦能被 lint/CI 强制化，立即迁出本文件改写成规则，此处只留一行迁移记录。

## 1. 测试策略分级

| 改动类别 | 要求 |
|---|---|
| 竞态/并发、资金、权限类 | **测试先行**：实现前先把事故场景写成会失败的测试，实现以让它们变绿为验收 |
| 一般业务逻辑 | 测试与实现同 PR 提交 + 行为层证据（实际运行输出/截图） |
| 纯 UI 样式、文档 | 不强制测试；视觉改动对照像素基准（landing 视觉零回归是根 CLAUDE.md 级硬约束） |

**不遵守的事故**：这三类代码出 bug 即真实损失（重复扣款、越权读取、任务双抢）；实现后补测试只会验证「我写的代码做了我写的事」，边界恰恰漏掉。测试先行同时是给 AI 实现者的验收合同——完成标准由红灯变绿判定，不由实现者自述。

**实证**：WP-3.3 任务系统（`SKIP LOCKED` 抢单）按测试先行交付，并发正确性一次通过（见 `docs/plans/phase-b-execution-plan.md`）。

**三类风险的固定事故场景清单**（出题模板，照单出题，不依赖临场灵感）：

- **并发/抢单**：①两个请求同时到达只能成功一个；②持有者中途崩溃后任务可被超时回收重领；③同一请求重复提交（重试/狂点）结果与提交一次等价（幂等）。
- **资金**：①金额 0/负数/超大值被拒；②支付渠道成功通知重复送达只入账一次（渠道真的会重发）；③价格以服务端报价为准，前端传值篡改无效；④渠道流水与订单表可对账。
- **权限**：①A 用户持 B 的资源 ID 访问被拒（404/403）；②未登录调用受保护接口 401；③普通用户调管理操作被拒。

## 2. 出入参运行时校验统一用 zod

进程边界的数据——API route 的请求入参与响应出参、Worker 任务 payload、外部服务回调——必须经 zod schema 校验后才进入应用层；schema 与 DTO 同处维护。

**不遵守的事故**：TypeScript 类型在运行时不存在，未校验的坏数据会穿透到数据库或支付逻辑深处才爆炸，排查成本数倍；多客户端（Web/App/小程序）接入后，服务端不能再假设入参形状。

**边界**：本条只拍板「运行时校验工具 = zod」（已是 `@petscape/server` 实际依赖）。**不预决**「接口契约正本」ADR（OpenAPI vs 代码 Schema，见 ARCHITECTURE §9 与待决策队列）；届时 zod schema 是候选正本形态之一。

## 3. 支付/订单上线前 checklist

来源：ARCHITECTURE §10 已拍板要求（「必须在支付与订单等高风险模块上线前就位」）。**现在一项都不做**；接支付前逐项打勾，未清零不上线：

- [ ] 接口限流与配额：单用户超频调用生成/上传类接口被拒（验收：超频请求返回 429 类拒绝）
- [ ] 备份恢复演练：从备份真实恢复出隔离实例并验证数据（WP-4.1 已演练；若因云侧备份未就绪而未完成，在此补做——见 `docs/plans/phase-b-execution-plan.md`）
- [ ] 部署回滚：回滚流程成文并真跑过一次（WP-4.2 已演练，上线前复核仍有效）
- [ ] 监控告警：支付失败率、任务失败率异常时主动通知到人，而非等用户上报
- [ ] 对账与异常恢复：渠道流水 vs 订单表定期核对；不一致订单有人工处理入口
- [ ] 审计记录：订单等关键状态变化留痕（谁/何时/从何值到何值）

**不遵守的事故**：收款后才发现无法回滚、无告警、对不上账——损失的是真金白银和用户信任，且事后没有还手余地。
